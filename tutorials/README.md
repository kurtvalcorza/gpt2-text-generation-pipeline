## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/gpt2_text_generation_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 15-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/gpt2_text_generation_input_manifest.json` with the schema, ceilings, the prompt's character count, the canonical greedy settings, the sampling settings validated alongside them, the verdict and one recorded rejection finding (an unseeded sampling request); `evaluation_report` (EVAL21) writes `outputs/gpt2_text_generation_evaluation_report.json`, whose verdict is always `not-measurable` because a continuation has no ground truth and no metric helper is shipped — the report names the held-out corpus (perplexity) or human raters that would make the task measurable (EVAL9), and says so even when a reference string is passed, because a reference string is not a corpus.
- The notebook exercises `GPT2TextGenerationPipeline` carried verbatim in the notebook rather than reimplementing model loading; the pipeline pins the immutable upstream revision, stages the missing snapshot file through the package's `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`), and refuses remote model code. No cell outside the carried module calls `transformers` or `huggingface_hub`, or the model's own `generate`.
- Decoding semantics (INF8/INF9): greedy (`do_sample=False`, the default) is presented as the deterministic reference mode and demonstrated with a byte-identical repeat call; nucleus sampling (`do_sample=True`, `temperature`, `top_p`, mandatory `seed`) is presented as the mode usually preferred for use and demonstrated with a same-seed repeat; every setting is validated before the model runs through the package's public `validate_settings` and echoed back in `settings`, and the export records both configurations.
- Pad/EOS quirk: GPT-2 ships no pad token; the pipeline fixes `PAD_TOKEN_ID = EOS_TOKEN_ID = 50256` in code and the notebook prints and explains it, including what `finished_by = 'eos'` means.
- No intrinsic metric exists (EVAL9): a continuation has no ground truth; the repository ships no metric helper; the notebook says so, names what a real evaluation needs (a held-out reference corpus for perplexity, or human judgements / a labelled downstream task), and presents its sanity checks (settings echoed, token budgets, determinism) as plumbing checks only. The model card's smoke completions are quoted as observations from one host, not expected values. Recorded `SHOULD` deviation: EVAL11 (no baseline — none is meaningful without a reference).
- Ceilings `CONTEXT_LENGTH`, `MAX_PROMPT_TOKENS`, `MAX_NEW_TOKENS`, `DEFAULT_MAX_NEW_TOKENS`, `MAX_TEXT_CHARS`, `VOCAB_SIZE`, `EOS_TOKEN_ID`, `PAD_TOKEN_ID` are surfaced before the model runs; the token-count ceilings are stated as checked by the pipeline after tokenisation (reject, never truncate) (DAT22/DAT23).
- The default sample is synthetic text authored in code; `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
